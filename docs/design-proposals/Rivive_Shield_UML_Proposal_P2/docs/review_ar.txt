 مذكرة مراجعة تحديث تصميم Rivive Shield

 الغرض من النسخة

هذه مذكرة لمراجعة تحديث حزمة UML والعقود بعد القرارات الأخيرة للمشروع. المطلوب هو الاتفاق على تصميم متسق قبل متابعة التطوير وفحص البيئة. وجود ملف تعريفات C++ أو رسم جديد لا يعني أن التطبيق نُفّذ أو أن التصميم اعتمد نهائيًا.

حالة الحزمة: مقترح للمراجعة. لا تمنح الحزمة الأعضاء إذنًا لإضافة حقول أو دوال أو كلاسات خارج UML المعتمد، ولا تعني اكتمال RS-06 أو RS-07. لا تعدّل هذه المذكرة التقرير الذي سبق تسليمه، ولا تسجل بذاتها أي تغيير في GitHub أو Trello.

 القرارات التي اتخذها أسامة

1. النموذج الأولي يعتمد على قواعد تشخيص وحلول محددة مسبقًا، دون مزوّد ذكاء اصطناعي خارجي. ذكر أسامة موافقة المحاضرة على هذا الاتجاه.
2. توضع قواعد التشخيص داخل كود DiagnosticAgent في هذه المرحلة. إضافة قاعدة مستقبلًا تستلزم تعديل الكود وإعادة بنائه. تحميل قواعد من ملف أو خدمة خارجية ليس جزءًا من القرار الحالي.
3. يعمل النظام كاملًا محليًا أولًا على أجهزة الفريق التي تستخدم Windows وmacOS. لا يشترط تشغيل Linux على أجهزة الأعضاء لإكمال هذه المرحلة.
4. لاحقًا يُنقل ما يلزم من باك إند الحجز وتطبيق الويب المستهدف إلى Oracle. يبقى برنامج Rivive Shield الرئيسي على أجهزة الأعضاء، ويكون العرض من جهاز أسامة.
5. يبقى الالتزام بالـUML إلزاميًا. حتى الحقول والدوال المساعدة أو الخاصة يجب إظهارها ومراجعتها ضمن تحديث التصميم قبل إضافتها.

هذه القرارات تحدد الاتجاه والنطاق، لكنها لا تعتمد تلقائيًا تفاصيل كل توقيع C++ أو أسلوب إدارة العمليات أو الاتصال البعيد المقترح في الحزمة.

 ما تغير بالنسبة إلى P1

كانت P1 تتضمن واجهة AiProvider ومحوّل RuntimeAiProvider وطلبات واستجابات وتدقيقًا مرتبطًا باستدعاء مزوّد فعلي. لم يعد هذا المسار مناسبًا للنموذج الأولي المتفق عليه. يجب إزالة اعتماده من التشخيص والتجميع والتدقيق والرسوم، بدل الاحتفاظ به وإرجاع إجابات ثابتة تحت اسم AI.

في النسخة المحدثة، يقرأ DiagnosticAgent الأدلة المتاحة ويطبق قواعد الكود المعروفة. يسجل التشخيص سبب النتيجة والأدلة التي استند إليها وهوية القاعدة أو إصدار مجموعة القواعد حسب العقد المقترح. هذا سجل قابل للمراجعة، وليس إثباتًا لاستدعاء نموذج ذكاء اصطناعي.

كما كانت P1 تصف مسارًا محليًا POSIX وتستعمل هوية عملية وتوقيت بدء في تصميم المهايئ. لا تكفي هذه الحقول وحدها لإثبات إدارة آمنة موحدة على Windows وmacOS. المطلوب فصل المسؤولية المشتركة عن تفاصيل ملكية العملية في كل نظام وإظهار تفاصيلها في العقود والرسوم. أي واجهة أو حقل جديد لهذا الغرض يبقى مقترحًا يحتاج المراجعة.

يجب قراءة سجل التغييرات والتواقيع الفعلي داخل الحزمة لمعرفة كل إضافة وحذف. هذه المذكرة تشرح المقصود ولا تستبدل المقارنة الدقيقة بين التعريفات.

 كيف يعمل التشخيص بالقواعد

التشخيص ليس اختيار إجابة بحسب اسم تجربة العطل. يجب ألا يحصل DiagnosticAgent على رقم سيناريو التجربة أو الإجابة المتوقعة ثم يعرضها باعتبارها استنتاجًا.

المسار المطلوب هو:

1. يستقبل الوكيل حادثًا مع أدلته وسياق التشخيص المسموح.
2. يقرأ ملاحظات الهدف المصرح بها، مثل حالة الخدمة ولقطة الحجوزات ونتيجة فحص التعارض.
3. يتحقق من كفاية الأدلة واتساقها وصلاحيتها للهدف الحالي، ضمن الحدود التي ستُراجع.
4. يطبق القاعدة المناسبة فقط إذا تحققت شروطها من الأدلة الفعلية.
5. يقترح إحدى عمليتي الإصلاح المسجلتين فقط، مع الأدلة وشروط التنفيذ وخطة التحقق.
6. تمر الخطة عبر PlanPolicy قبل عرضها للموافقة البشرية.

لا توجد خطة قابلة للتنفيذ عند نقص الأدلة أو تعارضها أو ظهور حالة غير معروفة. تسجل النتيجة بوضوح باعتبارها غير محسومة. لا يجوز أن تتحول قاعدة افتراضية من نوع «في غير ذلك أعد التشغيل» إلى طريق إصلاح عام.

إضافة قاعدة جديدة تستلزم مراجعة شروطها ومخرجاتها واختبار الحالات السلبية، مع تحديث UML والبطاقات إذا احتاجت حقولًا أو دوال أو أنواعًا جديدة. لا نضيف محرك قواعد مستقلًا أو ملفات قواعد ديناميكية دون قرار لاحق.

 النطاق الذي يجب أن يبقى محفوظًا

يبقى النموذج الأولي مخصصًا لتطبيق حجز غرف الدراسة والسيناريوهين المحددين، وليس أداة إصلاح عامة للأجهزة والشبكات:

- توقف خدمة الحجز، ثم إعادة تشغيل الخدمة المستهدفة عند ثبوت التوقف وتحقق شروط العملية والموافقة.
- تعارض حجزين ضمن الحالة المحددة، ثم حفظ الحجز الأسبق وإلغاء تعارض الحجز اللاحق وتفعيل منع التداخل وفق العقد الذري المقترح.

لا يُحذف الحجز المتعارض ولا تُصفّر قاعدة البيانات لإخفاء الخطأ. تحفظ السجلات اللازمة لإثبات ما حدث. تبقى عمليات التشخيص للقراءة، ولا تنفذ إصلاحًا أو تغيّر حالة الحادث بنفسها.

تظل الموافقة البشرية مرتبطة بالخطة المحددة وإصدارها ومعاملاتها ومدة صلاحيتها. تغيير الخطة لا يرث موافقة الخطة القديمة. نجاح أمر الإصلاح لا يعني نجاح التعافي: يجب إجراء التحقق المستقل وحفظ نتيجته قبل اعتماد Recovered.

تبقى عمليتا الحجز والتحكم منفصلتين، حتى لا يؤدي إيقاف خدمة الحجز إلى إيقاف البرنامج الذي يراقبها. ويبقى مخزن الحجوزات منفصلًا عن مخزن الحوادث، دون ادعاء وجود معاملة ذرية واحدة تغطي المخزنين.

 التشغيل المحلي وملكية العملية

على كل جهاز تطوير محلي، يجب أن يكون تشغيل الخدمة وإيقافها محصورًا في الهدف المعروف الذي أنشأه النظام وتحقق من ملكيته. معرفة PID فقط لا تكفي، لأن النظام قد يعيد استخدامه لعملية مختلفة.

يحتاج مسار Windows إلى مراجعة دورة حياة مقبض العملية المملوكة وكيفية الانتظار والإغلاق والإبلاغ عن الخطأ. ويحتاج مسار macOS إلى مراجعة ملكية العملية الابنة ومسؤولية الانتظار وجمع حالتها ومنع الإشارة إلى هوية أُعيد استخدامها. هذه متطلبات للمراجعة والاختبار، وليست ضمانًا بأن استخدام واجهة نظام بعينها يجعل التنفيذ آمنًا تلقائيًا.

يجب منع نسخ الكائنات التي تملك موارد العملية بصورة تؤدي إلى مالكين متعارضين. ولا يجوز إعادة تبني عملية قديمة بعد إعادة تشغيل برنامج التحكم دون مسار مصمم ومراجع. عند الشك في الملكية أو اكتمال الإجراء، تتوقف التغييرات وتُسجل الحالة للمراجعة.

لا تُستخدم أوامر shell عامة أو اسم برنامج أو مسار أو معاملات يوردها التشخيص. بدء الخدمة لأغراض الإعداد ليس طريقًا لتجاوز موافقة إصلاح حادث قائم. وبعد انتهاء مهلة الإجراء، لا نفترض أن العملية لم تتغير؛ نقرأ الحالة قبل تقرير الخطوة التالية.

 الانتقال اللاحق إلى Oracle

الاتجاه المعتمد هو نقل باك إند الحجز وتطبيق الويب المستهدف لاحقًا، مع إبقاء برنامج التحكم الرئيسي محليًا. هذا الاتجاه لا يحدد بعد قناة إدارة الخدمة البعيدة أو المصادقة أو الصلاحيات أو كيفية الوصول إلى الأدلة.

لا يصح نقل افتراض «عملية ابنة محلية» إلى الخادم كما هو. كذلك لا يكفي توفير API داخل خدمة الحجز لإعادة تشغيلها وهي متوقفة. يجب لاحقًا مراجعة قناة إدارة ضيقة أو مشرف منفصل يمكنه التحقق من الهدف وتنفيذ العملية المحددة وتسجيل النتيجة. لم يُعتمد هنا منتج أو بروتوكول بعينه.

يجب التمييز بين توقف التطبيق وتعذر الشبكة. انتهاء مهلة اتصال لا يثبت أن الخدمة توقفت، وانقطاع الرد بعد إرسال إصلاح لا يثبت أن الإصلاح لم يُنفذ. إعادة الإرسال العمياء غير مقبولة.

تظل تفاصيل مكان تخزين الحوادث عند النشر، والوصول إلى أدلة الحجوزات، وتنسيق أكثر من جهاز تحكم، ونظام تشغيل الخادم، وآلية المصادقة والتشفير والمكتبات قرارات مفتوحة. لا تستخدم ملفات SQLite المشتركة عبر الشبكة بديلًا غير مراجع عن واجهات واضحة. وتبقى خطوة Oracle منفصلة عن إثبات عمل النسخة المحلية.

 القيم التي لم تُعتمد بعد

لا تختار هذه المذكرة أرقامًا نهائية لعدد الأدلة أو أحجام النصوص أو المهلات أو طابور الأحداث أو حدود الفترات الزمنية. تضمنت P1 اقتراحات عددية، لكنها ليست قياسات أداء ولا موافقة جديدة من أسامة.

حد عدد دورات مزوّد AI لم يعد له معنى بعد إزالة المزوّد. أما حدود حجم البيانات ومدة التشخيص والعمليات والطابور فتحتاج قيمًا إيجابية ومحدودة يراجعها الفريق ويختبرها. لا يجوز إبقاء أرقام قديمة في الشرح وتقديمها على أنها متطلبات نهائية.

كذلك لم تحسم هذه المذكرة مخطط SQLite وترحيلاته وإعدادات المتانة والانتظار والمكتبة المستخدمة للاتصال. إذا تطلب حسمها تغيير نوع أو حقل أو دالة، يُراجع تغيير UML أولًا.

 مراجعة تطابق UML والعقود

راجعوا الحزمة بوصفها وحدة واحدة، لا ملف header وحده:

- كل class وstruct وenum وalias جديد له سبب واضح وحالة مقترح ظاهرة.
- كل حقل ودالة، بما فيها private والمُنشئات والمُهدمات وعمليات النسخ المحذوفة، ظاهر في الكتالوج والرسم التفصيلي المناسب.
- علاقات الوراثة والاعتماد والملكية توافق التواقيع الفعلية.
- لا يبقى اسم مزوّد AI أو اعتماد عليه في مسار التشغيل الجديد، بما في ذلك أمثلة التجميع والرسوم.
- تشرح الرسوم المعمارية أين يعمل كل جزء الآن، وتفصل المستقبل غير المحسوم عن المسار المحلي المقترح.
- إذا كان أحد الرسوم مختصرًا فلا يُستخدم وحده لإثبات تطابق جميع الحقول والدوال؛ المرجع التفصيلي هو قائمة التصريحات مع الرسوم الكاملة.
- أي تغيير غير متعلق بالقرارات الأخيرة يحتاج سببًا منفصلًا، ولا يُمرّر باعتباره مجرد تحديث صياغة.

 خطة التحقق قبل اعتماد التنفيذ

التحقق من التعريفات هو المرحلة الأولى فقط. يمكنه كشف أخطاء الأسماء والأنواع والوراثة والتصريحات، لكنه لا ينفذ الدوال ولا يثبت سلامة النظام.

| مجال التحقق | المطلوب إثباته | الحد الذي لا يتجاوزه |
| --- | --- | --- |
| تطابق الملفات | تطابق التصريحات مع الكتالوج والرسوم التفصيلية وتحديث المراجع المتأثرة | لا يثبت صحة منطق الدوال |
| فحص C++17 | قبول التعريفات وفحوص static_assert على المترجم الذي شُغّل فعلًا | لا يثبت linking أو دعم Windows وmacOS وقت التشغيل |
| التشخيص | كل حالة معروفة تعطي النتيجة المدعومة، والحالات الناقصة والمتعارضة تبقى غير محسومة | لا يعتمد على رقم سيناريو التجربة |
| الموافقة والتنفيذ | رفض الخطة المتغيرة أو المنتهية والموافقة المكررة والتشغيل غير المصرح | لا يجوز استبدالها بفحص واجهة المستخدم فقط |
| ملكية العملية | عدم التأثير على عملية غير مملوكة ومعالجة الخروج والتأخير وإعادة التشغيل | يُختبر على كل نظام مستهدف فعلًا |
| التخزين | ذرية إصلاح الحجز وحفظ المحاولات ومنع إعادة التنفيذ عند النتيجة غير المؤكدة | لا توجد معاملة واحدة بين ملفي SQLite |
| التحقق المستقل | سلامة الحجوزات السابقة وقبول الحجز الصحيح ورفض التعارض وتنظيف حجوزات الاختبار | نجاح عملية الإصلاح وحدها غير كافٍ |
| النشر البعيد | قناة إدارة وصلاحيات وقراءة نتيجة آمنة بعد الانقطاع | مؤجل إلى تصميم Oracle المراجع |

تشمل الحالات السلبية المهمة: وجود أكثر من تعارض، تغير إصدار الحجز قبل التنفيذ، تساوي توقيت إنشاء الحجزين، حجزان متزامنان، أدلة مفقودة، موافقة لخطة قديمة، فشل التخزين، نتيجة تنفيذ غير مؤكدة، فشل تنظيف حجز الاختبار، ونتائج تحقق ناقصة أو متناقضة.

لا تسجلوا أي صف في هذه الخطة باعتباره ناجحًا لمجرد وروده هنا. نتائج الفحص المنفذ ومترجمه وأمره وحدوده يجب أن تكون في سجل التحقق المصاحب. لم تُجرِ هذه المذكرة اختبارات تشغيل على أجهزة الفريق أو Oracle.

 خطوات الفريق بعد استلام الحزمة

1. يراجع أسامة وسامي التغييرات التنظيمية وحدود النشر وملكية العمليات، ويحدد الفريق القرارات التي ما زالت مفتوحة.
2. يراجع أصحاب الأجزاء التواقيع والحقول المرتبطة بعملهم، مع مراجع آخر وفق ترتيب المراجعة المتفق عليه. لا يعتمد العضو تغييره بنفسه.
3. في RS-06 تُراجع التعريفات التفصيلية والتطابق مع UML. وفي RS-07 تُراجع الحدود المعمارية والاتصالات وملكية الموارد. تجهيز الملفات وحده لا يكمل هاتين البطاقتين.
4. عند الاتفاق، تُوثق موافقة التصميم وتُحدّث البطاقات المتأثرة ومرفقات الشرح العربي بنفس نظامها السابق. هذه الحزمة لا تدعي أن تلك التحديثات نُفذت.
5. بعدها يُستكمل فحص التعريفات والأدوات على Windows وmacOS ضمن RS-03، دون اعتبار ذلك اختبارًا للتطبيق الكامل.
6. يبدأ تنفيذ أصغر مسار محلي حقيقي قابل للاختبار، ثم تتوسع الاختبارات تدريجيًا. يبقى الانتقال إلى Oracle مرحلة مستقلة بعد نجاح النسخة المحلية وتحديد الاتصال البعيد.

 نتائج التحقق المصاحبة لهذه النسخة

نجح فحص تصريحات C++17 باستخدام GCC 14.2.0 مع تفعيل التحذيرات كأخطاء. وتحقق آلي من تطابق الأنواع الـ63 وحقولها ودوالها ودرجات ظهورها بين ملف C++ والفهرس ورسوم UML التفصيلية. رُسمت ملفات Graphviz، وفُحصت الرسوم الرئيسية المتغيرة بصريًا. هذا ليس اختبارًا للتطبيق أو Windows أو macOS، ولا اختبارًا لسلامة إيقاف العمليات أو SQLite أو Oracle.

المقترحات الجديدة المحددة هي RuleAudit، وOwnedDemoProcess، وWindowsOwnedDemoProcess، وMacOwnedDemoProcess. وللتشخيص دالتان خاصتان ظاهرتان في الرسم: evaluateRules وrulesetVersion. تفصل ProcessStatus بين كون العملية جارية وبين صحة تطبيق الحجز. تعرض configuration الإعدادات الثابتة للتحقق من تطابق الهدف قبل أي أثر جانبي، ويستخدم خطأ الإعداد SetupError عند عدم التطابق. كل ذلك يحتاج مراجعة، ولا تعني سلامة التصريحات أن هذه الدوال نُفذت.
