# RS-06 item 1 v2: repository and history delta

Review candidate only. This is an explicit C++/UML/SQLite contract change from the frozen P3-R2 at 406ab2d, not an implementation or an approved migration. Findings 2 and 3 remain as accepted in the earlier rereview. This delta addresses Finding 1.

- **Write:** The coordinator selects an authorized pre-claim reason: PlanCancelled, PlanInvalidated, PlanExpired, or ControllerRestart. The repository operation `terminatePreparedAttempt` opens a write transaction, matches incident ownership and expected record version, and requires an open incident and the original Prepared attempt without a claim. The SQL insert makes the reason and UTC time durable; its trigger increments only recordVersion. It leaves incident status, incidentRevision, and unresolved effects unchanged. Any plan invalidation and incident transition still use existing reviewed rules; termination is not a new incident state or operation execution result.
- **Atomicity:** In the same transaction the repository rehydrates the resulting aggregate including the new termination, then appends its immutable record_history snapshot at the incremented version. Report SaveReceipt only after confirmed commit. Roll back if snapshot append or another pre-commit step fails. Never use save() to synthesize or delete a termination; it must preserve existing immutable entries. The schema guards alone do not implement the repository transaction contract.
- **Repeated calls and uncertain commit:** An existing termination with the same incident/attempt and same reason is a no-op: return the original receipt from the termination row and matching history version, not the guessed new event time. Conflicting reason or ownership is rejected. With no matching prior outcome, stale expected version fails. If commit is unconfirmed, reload the joined durable record and history before interpreting the result; no dispatch. If unavailable or inconsistent, block new action and report uncertainty.
- **Read:** load, loadPending and history reconstruct the original attempts alongside their append-only preparedTerminations, tied by attemptId. Live reads join canonical tables in one consistent snapshot; a historical version displays only terminations committed by that version, not later ones. Old records without terminations remain distinguishable from missing or inconsistent data. The existing OperatorView current/historyPage carries IncidentRecord, so no additional view field is needed. Show the original attempt as “not executed” with reason and UTC timestamp where an attached termination exists; never hide the attempt or infer termination solely from Prepared.
- **Restart:** Use the durable joined record. A terminated Prepared attempt is never dispatchable and does not alone block closure. An unclaimed, unterminated Prepared attempt from an old session can be retired under the approved rule. A claim or unresolved effect keeps the incident open; no replay. An unreadable or inconsistent record blocks new actions. Other close/recovery guards stay intact. Any later action requires a new valid plan and fresh approval.

### Item 5 transition clarification

After a confirmed termination, apply the existing PlanInvalidated transition separately, if applicable. If interrupted between those steps, reload the durable termination, do not dispatch the retired attempt, and reconcile invalidation before permitting any new attempt.
For an AwaitingApproval ManualStopProposal that invalidates the old plan, the same ordering applies: confirm any required termination and reason durably before invalidation. An existing claim or an unconfirmed outcome blocks this path; reconcile without replay and without starting another attempt. Do not introduce a new termination reason, repository operation, event, or state.
