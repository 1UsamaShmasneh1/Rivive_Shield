# جدول الحالات وواجهة الحجز للمراجعة

**المبادئ المعتمدة محفوظة؛ تفاصيل الجدول والمسارات أدناه مقترحة، وليست اعتمادًا شاملًا للعقد.**

## قواعد مشتركة
- حادث فعّال واحد لكل هدف، والملاحظات الجديدة تُضاف إليه دون إنشاء إجراءات موازية.
- كل موافقة مرتبطة بمعرف الحادث والخطة وإصدارها والهدف. الموافقة القديمة لا تنتقل إلى حادث أو خطة جديدة.
- تجاوز الحدود أو نقص الأدلة ينتج Unknown وتنبيهًا؛ لا إيقاف تلقائي. الحدود قابلة للضبط للتجربة، والمهلة تُحدَّد بالقياس لا بمتوسط عشوائي.
- الأحداث المتكررة ذات المعرف والمحتوى نفسه لا تُنفذ مرتين؛ اختلاف محتوى المعرف نفسه تعارض.
- أي انتقال غير مدرج يُرفض بلا إجراء. وصول ملاحظة لا يساوي الموافقة على خطة.

## جدول الانتقالات المقترح بين الحالات المعتمدة

الحالات التسع وأساس معانيها معتمدة. المنع المطلق لإغلاق حادث بأثر غير محسوم معتمد أيضًا؛ تفاصيل الانتقالات في الجدول لم تُعتمد بعد.
| الحالة | الحدث والشروط | الحالة التالية | النتيجة |
|---|---|---|---|
| لا حادث فعّال | ملاحظة تستدعي التحقيق أو طلب إجراء يدوي | Detected | إنشاء سجل جديد، لا تنفيذ |
| Detected | بدء تحليل الأدلة | Diagnosing | قواعد ثابتة فقط |
| Diagnosing | أدلة كافية وخطة مسموحة | AwaitingApproval | حفظ وعرض خطة محددة |
| Diagnosing | لا تشخيص كافٍ ولا إجراء جارٍ | Unresolved | تنبيه؛ لا إجراء تلقائي |
| AwaitingApproval | رفض الخطة المحددة | Declined | لا تنفيذ |
| AwaitingApproval | قبول صالح، حفظ ثم claim ذري، والهدف مطابق | Executing | إجراء واحد فقط |
| AwaitingApproval | موافقة قديمة/خاطئة/منتهية | AwaitingApproval | رفض الموافقة، لا تنفيذ؛ إعادة التقييم عند تغير الهدف |
| Executing | ثبت الإيقاف القسري | NeedsReview | حفظ التوقف وفحص SQLite بعد توقف الكتّاب؛ ليس تعافيًا |
| NeedsReview | ثبت التوقف وفحص القاعدة كافٍ، واقتراح بدء جديد | AwaitingApproval | خطة جديدة وموافقة جديدة؛ لا تشغيل فور الفحص |
| Executing | ثبت بدء العملية الصحيحة | Verifying | التحقق من النتيجة الوظيفية |
| Executing | ثبت فشل دون أثر جانبي | NeedsReview | تفسير الفشل، لا إعادة تلقائية |
| Executing | التنفيذ أو الحفظ غير محسوم | NeedsReview | منع التكرار والتشغيل التالي حتى الحسم |
| Verifying | أدلة عملية صحيحة وفحص قاعدة سابق صالح واختبار وظيفي مستقل | Recovered | حفظ النتيجة قبل عرض الاكتمال |
| Verifying | نتيجة وظيفية ناقصة/فاشلة أو مهلة تحقق منتهية | NeedsReview | لا ادعاء نجاح |
| أي حالة غير نهائية | نقص التقاط/تجاوز حد/ملاحظة جديدة | نفسها | إضافة الأدلة والتنبيه؛ منع أي إجراء لا يملك شروطه |
| أي حالة | تعارض هوية/حفظ يمنع الثقة بالإجراء | NeedsReview عند احتمال أثر، وإلا رفض الانتقال | لا تنفيذ جديد |

**تفاصيل تحتاج قرارًا:** أقترح اعتبار Recovered وDeclined وUnresolved حالات إغلاق فقط بعد التأكد من عدم وجود إجراء جارٍ أو أثر غير محسوم. NeedsReview يبقى فعّالًا ولا يُغلق لإنشاء حادث آخر يتجاوز الحظر. الإيقاف اليدوي من حالة غير تنفيذية يمر عبر إعادة تشخيص وخطة جديدة، وليس قفزة مباشرة إلى التنفيذ. بعد الإغلاق، طلب جديد يولّد حادثًا جديدًا مع موافقة جديدة. إذا أُضيفت أدلة تغيّر صلاحية خطة منتظرة، تُلغى صلاحية الموافقة ونرجع إلى Diagnosing.

**بداية التطبيق المتوقف أصلًا:** موافقة صريحة على الهدف قبل التشغيل، مع فحص قاعدة قائمة عند الحاجة؛ لا إنشاء بديل صامت. صياغة مسار أول إعداد داخل العقد يجب أن تُراجع أيضًا، دون اعتباره تجاوزًا لمسار الموافقات.

## مسارات API المعتمدة والتفاصيل المقترحة
الوظائف الثلاث ومنع التكرار ورفض المعرف ببيانات مختلفة معتمدة. المسارات الثلاثة التالية معتمدة الآن؛ الحقول ورموز HTTP التالية ما زالت للمراجعة:

| الطلب | الوظيفة | النتيجة المقترحة |
|---|---|---|
| GET /api/rooms | عرض الغرف | 200 وقائمة غرف |
| GET /api/bookings | عرض الحجوزات | 200 وقائمة حجوزات وإصدار snapshot |
| POST /api/bookings | إنشاء حجز ذري | 201 للجديد؛ 200 للطلب المطابق السابق |

حقول POST المقترحة: `requestId`, `roomId`, `startsAt`, `endsAt`, `label`. `requestId` معرف ثابت ينشئه العميل لكل نية حجز ولا يتغير عند إعادة نفس الطلب. الوقت UTC بصيغة موحدة؛ `startsAt < endsAt`؛ انتهاء حجز عند بداية آخر مسموح. `label` بيانات تجريبية، ولا يُحفظ محتوى HTTP في سجل المصحح.

الأخطاء المقترحة: 400 لبنية/قيم غير صالحة، 404 لغرفة غير موجودة، 409 للتداخل أو المعرف نفسه بمحتوى مختلف، 503 لقاعدة مشغولة/غير متاحة مؤقتًا، 500 لخلل داخلي غير متوقع. الرد يحتوي `errorCode` و`message` آمنين، دون SQL أو مسارات أو أسرار. ليس كل خطأ 500 عطل عملية، وليس كل 200 نجاحًا للمنطق الداخلي.

يبقى مطلوبًا: مخطط JSON الدقيق، حدود طول الحقول وحجم القوائم/صفحات النتائج، تطبيع المقارنة لنفس الطلب، مكتبة JSON، ومعاملة SQLite واختبارها. لا endpoint خاص للمصحح ولا cancel endpoint في المرحلة الحالية. يُختبر React الحقيقي ضمن HTTP/1.1 المحلي قبل قبول التكامل.


تحديث اعتماد الوقت: التخزين UTC والعرض بتوقيت جهاز العميل، والبداية قبل النهاية، والحجوزات المتجاورة مسموحة. تبقى أسماء حقول JSON وصيغة الوقت على الشبكة ورموز HTTP مفتوحة.


استكمال تقني: `schemas/state_policy_proposed.json` هو جدول سياسة شامل default-deny للمراجعة؛ النص هنا ملخص للقراءة. الأحداث غير المدرجة مرفوضة. لا أمر عام لإغلاق NeedsReview في هذه المرحلة، ولا تجاوز للأثر غير المحسوم. اكتملت في العقود مسارات طابور سجل الحوادث وحفظ الإعدادات بالخلفية، مع نتيجة غير متزامنة في عرض الواجهة.
