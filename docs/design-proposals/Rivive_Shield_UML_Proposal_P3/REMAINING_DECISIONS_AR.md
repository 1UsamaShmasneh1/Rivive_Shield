# القرارات المتبقية، بالترتيب المقترح

**كل توصية أدناه مقترح لم يُعتمد بعد. نراجع موضوعًا واحدًا في كل مرة، ثم نحدّث المشروع كله دفعة واحدة.**

## 1. سلوك الحوادث والموافقة، اعتمد المبدأ وتبقى التفاصيل
اعتمدت وجود حادث فعّال واحد للهدف في كل لحظة وتجميع الملاحظات ومنع الإجراءات المتزامنة وعدم نقل موافقة قديمة لحادث جديد. وتوصيتي المتبقية: الحدث الجديد يضاف إلى الحادث المفتوح بدل تكرار نوافذ الإصلاح. الحادث المكتمل أو المرفوض يحتفظ بسجله؛ طلب إصلاح جديد ينشئ حادثًا جديدًا ولا يعيد فتح موافقة قديمة. أثناء تنفيذ إجراء لا نقبل إجراءً ثانيًا.

كل موافقة ترتبط بالإجراء والهدف وإعداداته المحددة. إذا تغير الهدف أو أُعيد تشغيل المصحح نلغي صلاحية الموافقات القديمة، ولا نعيد إجراءً لم نعرف هل نُفّذ أم لا. يتطلب جدول UML انتقالًا صريحًا لكل حالة، لا عبارة «أي حالة» فضفاضة.

المتبقي: جدول الانتقالات الكامل، وشروط إغلاق الحوادث غير المحسومة ومعالجة سجل جديد بعد الإغلاق. لا نتجاوز إجراءً غير محسوم بإنشاء حادث جديد.

## 2. واجهة الحجز بين React وC++
اعتمدت وظائف عرض الغرف وعرض الحجوزات وإنشاء حجز، ومنع تكرار الطلب نفسه بمعرفه نفسه. المسارات GET /api/rooms وGET /api/bookings وPOST /api/bookings معتمدة الآن. JSON ورموز HTTP وتفاصيل الوقت أدناه ما زالت مقترحة. الإلغاء مؤجل كما وافقت. كل حجز يحمل معرف طلب ثابتًا: تكرار الطلب نفسه يعيد النتيجة السابقة، ولا ينشئ حجزًا ثانيًا؛ لا يعني ذلك أن المصحح سيحفظ الطلب أو يعيد إرساله.

الوقت بصيغة UTC، وبداية المدة أصغر من نهايتها؛ انتهاء حجز عند بداية آخر لا يعد تداخلًا. نقترح 201 للحجز الجديد، 200 لإعادة نفس النتيجة، 400 للمدخل غير الصالح، 409 للتعارض، و503 لتعذر التخزين مؤقتًا. نحسم أسماء JSON والتحقق منها قبل تنفيذ واجهة React.

## 3. سياسة SQLite والملفات
اعتمدت قاعدتين منفصلتين: الحجوزات والحوادث، وعدم إنشاء بديل بصمت لملف قائم مفقود أو تالف، والفحص بعد توقف الكتّاب. إنشاء القاعدة الجديدة خطوة إعداد صريحة لا تقع تلقائيًا عند فقدان أو تلف ملف قائم. أقترح WAL وsynchronous=FULL للتجربة، مع اختبارهما على Windows وMac؛ لا نعتبر ذلك ضمانًا ضد كل انقطاع كهرباء. نفحص سلامة البنية والمفاتيح الأجنبية بعد الإيقاف وتوقف جميع الكتّاب، ولا نحذف ملفات WAL/SHM.

## 4. حدود التشغيل والمراقبة
أنصح بإعدادات محدودة بدل أرقام بلا حد، ثم قياسها بالتجارب. نقطة بداية مقترحة للمراجعة: 32 اتصالًا، 8 أزواج HTTP متتابعة لكل اتصال كما في التجربة، ميزانية قبول تراكمية 8 MiB لكل دورة مراقبة، وطابور 256 حدثًا. الميزانية ليست قياسًا دقيقًا لاستهلاك الذاكرة؛ نختبر قيود المكتبات أيضًا. بلوغ الحد ينتج عدم يقين وتنبيهًا، لا قتل التطبيق.

نحدّد مهلة العملية لكل نوع تجربة بعد القياس، ولا نستعمل متوسطًا بسيطًا كدليل قطعي على التعليق. لا نفعّل إيقافًا قسريًا تلقائيًا. السياسة الرقمية النهائية تعتمد بعد تجارب تحميل صغيرة، لا اعتمادًا على المقترحات وحدها.

## 5. الواجهة والبناء والتوزيع
أنصح بواجهة سطح مكتب بسيطة تعرض حالة الهدف، الحادث والأدلة وخطة الإجراء وأزرار الموافقة/الرفض. عمل المراقبة والتخزين بالخلفية، لا في خيط الواجهة. لا يتسبب إغلاق المصحح تلقائيًا في قتل تطبيق الحجز.

نثبت إصدارات المكتبات التي سنستخدمها بعد اختبار توافقها، ولا نرفع نواتج Windows الثنائية باعتبارها جاهزة للـMac. يظل قرار تأجيل CMake للمشروع قائمًا ما لم تغيّره أنت. نراجع طريقة بناء كل نظام قبل اعتبار تجهيز الفريق مكتملًا.

اعتمد المستخدم توزيع جميع البطاقات والمراجعين وإضافة RS-31 كما في `APPROVED_ASSIGNMENTS_AR.md`. React والمراقبة المعقدة لأسامة؛ GUI وSQLite لأمين؛ القواعد لشهاب. هذا اعتماد للتوزيع ولا يثبت تنفيذه في اللوحة. لا ننقل مسؤولية عضو بصمت.

## 6. إغلاق المخطط قبل النشر
بعد القرارات السابقة نراجع توقيعات الكلاسات، جدول الحالات الكامل، مخطط SQL، مخطط JSON، وتوصيل الواجهة بالـruntime. تشمل المراجعة مسار أول تشغيل والموافقة عليه، لا مسار الإصلاح فقط. بعدها تصبح نسخة UML واحدة مرجع التنفيذ وتُحدّث البطاقات وREADME وملفات الشرح معًا.

نتائج Mac وتكامل النظام الفعلي شروط قبول لاحقة وليست نجاحًا مفترضًا. إدارة Oracle عن بُعد ليست جزءًا مكتملًا من المخطط المحلي، وتحتاج مراجعة منفصلة عند الانتقال إليها.

## إنشاء الحجز كوحدة واحدة: اعتمد المبدأ، وتبقى الإعدادات
منع التداخل ومنع تكرار الطلب يجب أن يُنفّذا داخل معاملة كتابة واحدة، مع معرف فريد في قاعدة البيانات. الطلب المطابق يعيد النتيجة السابقة؛ اعتمدت رفض محتوى مختلف يحمل المعرف نفسه، بدل استبدال الحجز. رمز HTTP الخاص به لم يُعتمد بعد.

نضيف تراجعًا صريحًا عند الفشل قبل الالتزام، ومعالجة محدودة لقاعدة مشغولة بدل إعادة المحاولة بلا نهاية. خطأ قيد SQLite لا يعني تلقائيًا إلغاء المعاملة كلها؛ افتراضيًا قد يُلغى الأمر الفاشل وحده. نختبر الطلبات المتزامنة والانهيار قبل/بعد commit، ونفرّق بين حفظ الحجز ووصول الرد للعميل. اعتمدت المعاملة الذرية والتراجع والرفض واختبارات التزامن والتوقف. تبقى إعدادات SQLite مثل WAL وsynchronous ومهل إعادة المحاولة مفتوحة.


تحديث اعتماد الوقت: التخزين UTC والعرض بتوقيت جهاز العميل، والبداية قبل النهاية، والحجوزات المتجاورة مسموحة. تبقى أسماء حقول JSON وصيغة الوقت على الشبكة ورموز HTTP مفتوحة.
